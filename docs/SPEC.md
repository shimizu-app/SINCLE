# SYNCLE 開発仕様書

名刺から始まる営業CRM。名刺をスキャンして顧客を登録し、チームで商談を進める。

このドキュメントは Claude Code に実装を依頼するための仕様書です。
デザインの見本は `syncle-v28.jsx`（React単一ファイルのプロトタイプ）を参照してください。

---

## 0. Claude Code への指示

### 守ってほしいこと

- **勝手に技術を変えない。** 下記の構成から外れる場合は必ず確認を取る
- **一度に全部作らない。** 「9. 実装の順番」のフェーズごとに区切り、動く状態にしてから次へ進む
- **プロトタイプは見た目の参照。** ロジックはこの仕様書を正とする
- **RLS（行レベルセキュリティ）を最初から有効にする。** 後付けは事故のもと
- **型を先に定義する。** `types/` にデータ型を置き、それを基準に実装する

### 最初にやること

1. このファイルと `DATABASE.md` `SCREENS.md` を読む
2. `syncle-v28.jsx` をブラウザで確認し、デザインの方向性を把握する
3. フェーズ1の実装計画を立てて提示する（実装はその後）

## 1. 技術構成

| 領域 | 使うもの | 補足 |
|---|---|---|
| フレームワーク | Next.js 15（App Router） | TypeScript |
| UI | React 19 + Tailwind CSS | プロトタイプと同じ |
| アイコン | lucide-react | 独自SVGシェイプも併用（後述） |
| DB / 認証 / ストレージ | Supabase | Postgres + Auth + Storage |
| リアルタイム | Supabase Realtime | チャンネル・DM用 |
| ホスティング | Vercel | |
| 名刺OCR | Google Cloud Vision API | フェーズ4で導入 |
| AIメール | Anthropic API（claude-sonnet-4-6） | フェーズ5で導入 |
| 外部連携 | Google Calendar / Gmail API | フェーズ6で導入 |

### 使わないもの

- 状態管理ライブラリ（Redux等）。React の状態と Supabase のクエリで足りる
- ORM（Prisma等）。Supabase のクライアントを直接使う
- UIライブラリ（MUI等）。デザインが独自なので邪魔になる

## 2. このアプリの中心にある考え方

**入力を強制しない。** 記録が作業の副産物として発生する設計にする。

| きっかけ | 自動で起きること |
|---|---|
| 名刺を登録 | 会社作成 → チャンネル作成 → ティア自動判定 → 初回フォロータスク生成 |
| 同じ会社の名刺を登録 | 既存会社に追加（新規作成しない） |
| メールを送信 | メール履歴 + チャンネル通知 + タイムライン記録 |
| 進捗ステージを変更 | チャンネル通知 + タイムライン記録 |
| 日程を確定 | カレンダー登録 + 会議リンク + 準備タスク + チャンネル通知 + 確認メール |
| タスクを追加 | チャンネル通知 + カレンダー登録（任意） |
| 案件メモを更新 | 「最終更新」がリセットされ、放置判定から外れる |

この連鎖がこのアプリの価値。画面だけ作っても意味がない。

## 3. 主要な概念

### 会社が起点

```
Workspace（会社アカウント）
└── Company（顧客企業）        ← すべての起点
    ├── Contact（名刺）× 複数
    ├── Deal（案件）× 1        ← 当面は1社1案件
    ├── Task × 複数
    │   └── Subtask × 複数
    ├── Mail × 複数
    ├── Event（打合せ）× 複数
    ├── Document（書類）× 複数
    └── Channel（社内チャット）× 1
```

### ティア自動判定

名刺の役職と企業規模から、会社のランクを自動で決める。

**役職スコア**
| 判定 | 含まれる語 | 点 |
|---|---|---|
| 決裁者 | 代表, 社長, CEO, COO, CFO, CTO, 役員, 取締役, 専務, 常務 | 3 |
| 部門長 | 本部長, 事業部長, 部長 | 2 |
| 管理職 | 課長, マネージャー, リーダー, 室長, 主任 | 1 |
| 担当者 | それ以外 | 0 |

**規模スコア**：300名以上 = 2、50〜299名 = 1、それ未満 = 0

**合計** 4点以上 = A、2〜3点 = B、0〜1点 = C

会社単位では、所属する名刺のうち最高スコアで判定する。手動での上書きも可能。

### 案件の放置判定

案件の状況ごとに、何日動かないと警告を出すかを変える。

| 状況 | しきい値 |
|---|---|
| 商談中 | 7日 |
| 提案準備中 | 5日 |
| 見積提出済 | 7日 |
| 制作進行中 | 10日 |
| 確認待ち | 5日 |
| 保留 | 30日 |

しきい値を超えたらオレンジ、2倍を超えたら赤。メモを更新すると `updated_at` が更新され、判定がリセットされる。

## 4. 権限とセキュリティ

### ワークスペース分離

- すべてのデータは `workspace_id` を持つ
- Supabase の RLS で、自分が所属するワークスペースのデータのみ参照・更新可能にする
- **これを最初に設定する。** 機能を作ってから後付けしない

### メンバーの参加経路（3つ）

1. **事前登録** — 管理者がメールアドレスを登録。本人がログインした時点で参加
2. **同ドメイン申請** — 同じメールドメインの人が申請 → 管理者が承認
3. **招待リンク** — 有効期限つき・使用回数制限つきのURL

### 認証

- パスワードなし。メールアドレスに6桁コードを送る（Supabase Auth の OTP）
- Google OAuth も用意（Gmail / Calendar 連携の許可もここで取る）
- ログイン状態は保持。端末側の生体認証でアプリのロックを解除する

## 5. デザイン

`syncle-v28.jsx` を参照。要点だけ記す。

### 配色

```
背景        #FDFAF4   カード     #FFFFFF   罫線   #EDE7DC
文字        #141414
purple #8851D8   blue #3E86ED   green #2A9D67   red #EA392B
pink   #F58BB4   yellow #F9C22E  orange #F2811D  lime #A5D99E
```

各色に淡い版（SOFT）がある。プロトタイプの `SOFT` オブジェクトを参照。

### フォント

```
'M PLUS Rounded 1c', 'Zen Maru Gothic', system-ui, sans-serif
letter-spacing: 0.015em
```

### 形

**角丸を統一しない。** `22px 11px 22px 11px` のような左右非対称を基本とし、隣り合う要素で反転させる。プロトタイプの各コンポーネントを参照。

**独自のSVGシェイプを使う。** 花・クローバー・太陽・blob・六角・バースト・スタンプ・しずく・雲・波・アーチ・変形スクエアの12種類。プロトタイプの `SHAPES` オブジェクトのパスをそのまま使う。会社アイコンは業種から形と色を自動で決める。

### モーション

- イージングは `cubic-bezier(.22,1,.36,1)`、跳ねる動きは `cubic-bezier(.34,1.56,.64,1)`
- 全ボタンに共通の押下挙動（沈む → 跳ねて戻る → 押した位置から色が広がる）
- `prefers-reduced-motion` で全アニメーションを無効化する

## 6. 外部連携の注意点

### Gmail

- **受信箱全体を表示しない。** 顧客リストに登録されたアドレスとの送受信だけを取り込む
- 取り込み範囲は3段階（登録した相手だけ / 会社のドメインまで / 受信箱すべて）。既定は1番目
- **自分が送ったスレッドへの返信は、範囲設定に関わらず必ず取り込む**
- 権限スコープは必要最小限に。審査があるので早めに申請する

### Google Calendar

- 空き時間の判定は freebusy エンドポイントを使う（予定の中身は読まない）
- **チーム共有は購読方式にする。** 共有カレンダーを1つ作って全員が購読する。各人のカレンダーに個別作成すると、修正・削除のたびに全員分を書き換えることになり破綻する
- タスクの期限を通常の予定として入れると空き時間が埋まって見える。専用カレンダーに分けるか Google ToDo 側に入れる

### Google Meet

- 予定作成時に `conferenceData` でリンクを自動発行できる
- **Zoom は Google API では発行できない。** 固定URLを設定に登録して差し込む方式にする

### AIメール

- 必ず下書きとして表示し、送信は人が押す
- 金額・納期・実績は生成させない（ハルシネーションの危険がある）
- コンテキストとして渡すもの：会社名・担当者名・役職・業種・従業員数・案件種別・案件内容・進捗ステージ・社内メモ・未完了タスク・トーン・自由記述・返信元メール

### 予約ページ（日程調整）

ログイン不要で外部に公開するため、以下が必須。

- 推測されにくいトークン（32文字以上のランダム文字列）
- 有効期限
- 確定後は無効化
- **確定直前にカレンダーを再確認してダブルブッキングを防ぐ**

## 7. 実装で気をつけること

### 名刺の重複

会社名を正規化（「株式会社」「有限会社」「合同会社」と空白を除去）して近いものを検出し、「もしかしてこれですか」と確認を出す。完全一致だけで判定すると「株式会社アルテック」と「アルテック」が別物になる。

### 顧客リストの表示

プロトタイプではスクロール連動のカードデッキになっている。**200社を超えると目的の会社に到達できない。** 実装時は以下のどちらかにする。

- 絞り込み結果が10件以下のときだけデッキ、それ以上は通常リスト
- デッキは「今日フォローすべき数社」専用にして、全顧客リストは通常リスト

### 画像の扱い

プロフィール写真は、アップロード時に正方形に切り抜いて256px程度に縮小する。原寸のまま保存すると容量を食う。

### 案件が複数になったら

現状は1社1案件。並行案件が発生したら `deals` を独立したテーブルに分離する必要がある。その際タスクも案件にぶら下げ直すことになるので、**早い段階で判断する。**

## 9. 実装の順番

**フェーズごとに動く状態にしてから次へ進むこと。**

### フェーズ1：土台（最優先）

- Next.js + Supabase のセットアップ
- データベースのテーブル作成と RLS 設定
- 認証（メール + 6桁コード）
- ワークスペースの作成と参加
- デザインシステム（色・フォント・SVGシェイプ・共通コンポーネント）

**完了条件**：ログインしてワークスペースに入れる。中身は空でよい。

### フェーズ2：名刺と顧客

- 名刺の手入力登録
- 会社リスト（通常リスト形式でよい）
- 会社詳細の概要タブ
- ティア自動判定
- 検索・絞り込み・並べ替え

**完了条件**：手入力で顧客を登録して一覧で見られる。

### フェーズ3：タスクとチャンネル

- タスクのCRUD、チェックリスト、カレンダー表示、メモ
- 会社チャンネル（自動生成）
- グループチャンネル
- 個人チャット（DM）
- Realtime での同期
- メンバー招待（3経路）

**完了条件**：チームで使い始められる。

### フェーズ4：名刺スキャン

- カメラ撮影
- Google Cloud Vision でのOCR
- 読み取り結果の確認画面
- 既存会社との突き合わせ

**完了条件**：名刺を撮って登録できる。

### フェーズ5：案件と書類

- 案件の状況・メモ・放置判定
- 進行中リスト
- 書類のアップロードと分類（Supabase Storage）
- キーパーソン
- 活動タイムライン

**完了条件**：案件の進み具合が見える。

### フェーズ6：外部連携（最後）

- Google Calendar 連携
- 日程調整と予約ページ
- Gmail 連携
- AIメール作成

**完了条件**：全機能が揃う。
